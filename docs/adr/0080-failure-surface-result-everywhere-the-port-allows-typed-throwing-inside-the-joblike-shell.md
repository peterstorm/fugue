# ADR-0080: Failure surface — `Result` everywhere the port allows; typed throwing inside the `JobLike` shell

## Status
Accepted

## Date
2026-08-14

## Context
The file backend introduces filesystem, decoding, clock, replay, and observability failures at three durable ports. The `Checkpointer` and `FreshnessIndex` contracts already return `Result<_, FrameworkError>`, and the new event-log readers and `resumeFileJob` can adopt the same explicit channel. The kernel's existing `JobLike` contract is different: `updateData`, `updateProgress`, and `appendEvent` return `Promise<void>`, while `data` is a getter. There is no `Result` channel available without changing the kernel contract, which FR-001 and FR-042 require the backend to preserve.

Failures must remain attributable without expanding the closed framework error taxonomy. FR-040 requires typed failures and no raw throw across boundaries that can represent an error, while backend-swap parity requires existing meanings such as `checkpoint-corrupt`, `checkpoint-expired`, `checkpoint-version-mismatch`, `checkpoint-write-failed`, `checkpoint-missing`, and `cache-error`. Durability also forbids swallowing a failed append or checkpoint write: the transition must abort so retry can re-derive the same append rather than advance from bytes that were never committed.

The runtime boundary is hostile rather than merely type-checked. JavaScript callers can bypass brands, pass accessors or proxies that throw arbitrary values, inject failing clocks or decoders, and persist codec-valid payloads that make `machine.transition` or `machine.stateKey` throw. Required corruption warnings can fail too. Error handling must therefore be total even while handling an earlier failure, and the file backend must do so without new dependencies: FR-041 permits only `node:fs`, `node:crypto`, and `node:path` among Node built-ins and no added package dependency.

## Options Considered

1. **Preserve the ports: return `Result` wherever signatures admit it and throw through `JobLike`'s existing shell**
   - Pros: Preserves source and behavioral compatibility; makes every operational failure explicit where a typed channel exists; lets failed durable writes abort the kernel transition; reuses the established `FrameworkError` taxonomy and Redis/BullMQ surface conventions; requires no dependency.
   - Cons: The public file surface has two transport styles (`Result` and throw), though both are closed over the same `FrameworkError` taxonomy; `JobLike` consumers must catch typed rejected values rather than match an `Err`.

2. **Change `JobLike` methods to return `Promise<Result<void, FrameworkError>>`**
   - Pros: Gives every durable operation one explicit, typed error channel and makes throws unnecessary in conforming adapters.
   - Cons: Breaks the kernel contract and every existing adapter and caller; violates FR-001 and FR-042; expands F6 from a backend addition into a framework-wide migration. This was not viable under the compatibility constraint.

3. **Swallow `JobLike` failures or report apparent success**
   - Pros: Keeps the kernel running and avoids promise rejection handling in callers.
   - Cons: Can advance state after an event or checkpoint failed to persist, violating append-before-checkpoint ordering and crash recovery; converts data loss into false success; prevents retry from re-deriving the failed transition.

4. **Add file-specific error kinds or allow raw runtime exceptions through**
   - Pros: A `file-io` kind could distinguish filesystem storage from other caches, while raw exceptions require less boundary code.
   - Cons: Expands the closed public union without a new recovery behavior; diverges from Redis parity; forces downstream exhaustive handlers to change; raw `TypeError`, `RangeError`, hostile thrown values, and logger exceptions would violate FR-040 and make diagnostics unreliable.

## Decision
**Preserve the existing port signatures: return `Result<_, FrameworkError>` from every Result-bearing operation, and use the existing throwing channel inside `JobLike`, with typed `FrameworkError` throws for infrastructure failures.**

The choice is forced for `JobLike` once compatibility is fixed: `Promise<void>` and a synchronous getter provide no value-level error channel. The shipped implementation therefore uses these concrete surfaces:

| Surface | Shipped failure behavior |
|---|---|
| `Checkpointer.setMeta` / `saveNode` in [`file/checkpointer.ts`](../../packages/framework/src/file/checkpointer.ts) | Invalid identifiers, malformed options/state, and non-lossless metadata or node output return `checkpoint-write-failed`; filesystem and clock failures return `cache-error` with operation `setMeta` or `saveNode`. |
| `Checkpointer.load` | Invalid runtime input, unreadable storage, parser defects, and clock failures return `cache-error(load)`; invalid metadata returns `checkpoint-corrupt`; version or expected-DAG-fingerprint disagreement returns `checkpoint-version-mismatch`; lazy TTL expiry returns `checkpoint-expired`; missing metadata returns `ok(null)`. |
| Per-node checkpointer corruption | The entry is dropped and its discriminated address is added to `corruptNodeAddresses` (`node-key` when recoverable, otherwise `digest-filename`). The port-owned `reportCorruptCheckpointEntry` policy requires `fwLogger().warn`; if warning throws, both Redis and file loads return their typed `cache-error(load)` operation rather than rejecting raw or silently claiming the corrupt drop was observed. |
| `FreshnessIndex.recordWrite` / `hasRecordedWrite` / `findConflict` in [`file/freshness-index.ts`](../../packages/framework/src/file/freshness-index.ts) | Boundary, accessor/proxy, clock, codec, and filesystem failures return `cache-error` under `freshness:recordWrite`, `freshness:hasRecordedWrite`, or `freshness:findConflict`. Lock-protocol failures — the closed set `acquireFileLock` / `withFileLock` / `releaseFileLock` / `stealStaleFileLock` that atomic.ts produces, including body-internal failures (e.g. the `atomicWriteFile` commit) wrapped by `withFileLock` — are RE-TAGGED at this public surface to the caller's operation, mirroring the journal's `appendEvent` re-tag: the lock detail (lock path, the primary body failure nested inside the `withFileLock` diagnostic) stays in the message chain and the inner `failureClass` is preserved. Any other already-typed failure (port operation or body-internal operation) rides through unchanged; untyped throws are wrapped. A malformed stored singleton on either query returns a typed `cache-error` and withholds the conflict/acknowledgement verdict, matching ADR-0079 and the Redis adapter's fail-closed handling of undecodable persisted evidence; corruption is never converted to `ok(null)`/`ok(false)`. |
| `readFileEventRecords` / `readFileEvents` in [`file/event-log.ts`](../../packages/framework/src/file/event-log.ts) | Missing `events/` returns an empty successful log. I/O, JSON, schema, sequence, filename, digest, and bounded-depth failures return `cache-error` naming the reader operation and offending path; no corrupt event is skipped. |
| `resumeFileJob` in [`file/resume.ts`](../../packages/framework/src/file/resume.ts) | No recoverable state returns `checkpoint-missing`. Event-log read/proof failure, checkpoint decode failure, disagreement, and throws from deserialization, caller `parseCheckpoint`, `machine.transition`, or `machine.stateKey` return `checkpoint-corrupt` with the file or replay step named. A typed `cache-error` thrown while reading `checkpoint.json` passes through unchanged; an unrecognized throw is re-tagged rather than asserted to be typed. |
| `FileJournal` in [`file/journal.ts`](../../packages/framework/src/file/journal.ts) | Every rejected journal operation throws a typed `FrameworkError` of kind `cache-error`: invalid FR-015 dedup keys, invalid progress, forged checkpoint commits, hostile clocks, and filesystem/lock/listing/capacity/atomic-read/write/release failures. `writeCheckpoint` accepts only the opaque, runtime-capability-checked output of `serializeFileCheckpoint`, never arbitrary JSON. The `operation` field is exactly `appendEvent`, `writeCheckpoint`, `writeProgress`, `readCheckpoint`, or `createFileJournal` for factory configuration; the message names the durable directory/file. An append whose body committed but whose owned lock could not be released rejects as `appendEvent`; a simultaneous body and release failure preserves the body failure as primary. |
| `createFileJob` / `JobLike` in [`file/job.ts`](../../packages/framework/src/file/job.ts) | Every rejected adapter operation throws a typed `FrameworkError` of kind `cache-error`: non-lossless event/checkpoint values, unclonable snapshots, hostile caller values, and wrapped journal failures. The `operation` field is exactly `appendEvent`, `updateData`, `updateProgress`, `data`, or `createFileJob` for factory configuration. The initial seed and every update are reconstructed from the exact validated checkpoint bytes before any caller-owned reference can become working state; `updateData` writes the opaque commit and advances only to its detached snapshot after persistence succeeds. |
| Exported throwing codecs and module-exported internal helpers | `serializeFileCheckpoint`, `serializeFileEventRecord`, and `assertLosslessEvent` are exported by the public [`src/file.ts`](../../packages/framework/src/file.ts) subpath barrel. The atomic/lock helpers are exported only from their implementation module for internal reuse and focused testing; they are **not** public file-barrel exports. Both categories throw only typed `cache-error` values with helper operation and record/path context. Their read-side parsers remain explicit `Result` values. |
| File factories | Invalid directory/options, hostile reflection traps, and non-function clocks throw typed `cache-error` with operation `createFileJournal`, `createFileJob`, `createFileCheckpointer`, or `createFileFreshnessIndex`; no eager `TypeError` leaks. |

The throwing shell is closed over `FrameworkError`. The absence of a `Result` channel changes only transport, not taxonomy: invalid dedup/progress values, non-lossless event/checkpoint values, unclonable snapshots, factory validation, hostile runtime behavior, and I/O all become existing `cache-error` values with precise operation/path context. No new kind is introduced. A backend-local closed `FileOperation` literal union constrains `fileOperationError`, Result-bearing file cache failures, and every file-backend operation call site, so an operation typo fails typechecking. The public `cache-error.operation` field and `frameworkError.cacheError` factory remain `string`-typed for compatibility with other adapters. Low-level pure implementation functions may use local exceptions as control flow, but every exported throwing boundary catches and converts them before they can escape.

Total handling is implemented rather than assumed:

- [`types/safe-error.ts`](../../packages/framework/src/types/safe-error.ts) and [`file/boundary-error.ts`](../../packages/framework/src/file/boundary-error.ts) provide total diagnostic rendering and errno probing for arbitrary thrown values, including throwing `message`/`code` getters and revoked proxies. [`types/errors.ts`](../../packages/framework/src/types/errors.ts) provides the closed `FrameworkError` discriminant guard. Best-effort secondary cleanup diagnostics use a logger-safe path, so a hostile host logger cannot replace a primary body failure. Owned-lock release failure itself is not warning-only: it throws typed `cache-error(releaseFileLock)`, is surfaced as `withFileLock`/`appendEvent` when the body succeeded, and remains secondary only when a primary body failure already exists. Result-bearing required-warning paths still return `cache-error` if observability fails.
- Checkpointer and freshness methods snapshot caller-owned fields before validation, contain accessor/proxy and clock throws, and never let a required warning transport failure escape or disappear. Persisted Checkpointer adapters share the port-owned `reportCorruptCheckpointEntry` policy, so Redis and file cannot drift on this Result contract.
- Resume guards every untrusted decoder, transition, state-key, and serializer-tag seam. Event codecs use bounded/iterative hostile-data walks, so excessive nesting becomes a contextual typed read failure rather than a raw stack-overflow `RangeError`.
- Corrupt bytes and environmental failures retain distinct behavior where the port contract distinguishes them; where resume cannot prove an authoritative log, it fails closed as `checkpoint-corrupt` while preserving the underlying path and reason.

FR-041 is a mechanically enforced architectural boundary of the implementation. Every Node built-in import under [`packages/framework/src/file/`](../../packages/framework/src/file) or the [`src/file.ts`](../../packages/framework/src/file.ts) barrel must be exactly `node:fs`, `node:crypto`, or `node:path`; all other imports are existing framework-relative modules, and `packages/framework/package.json` adds only the `./file` export, not a dependency. The spelling decision is explicit: the three approved capabilities must use canonical `node:` specifiers. Legacy bare spellings (`fs`, `crypto`, `path`) are recognized as the same built-ins but rejected with an actionable canonical replacement; built-in subpaths such as either `node:fs/promises` or `fs/promises` are recognized after normalization and remain outside the exact allow-list. The file-scoped rules in [`scripts/check-imports.ts`](../../packages/framework/src/scripts/check-imports.ts) derive a robust built-in inventory from `node:module`, normalize canonical and bare forms, and fail closed on any `node:` namespace entry unknown to the running inventory. They preserve rejection of bare, relative, dynamic, side-effect, require, and re-export paths to `bullmq`, `ioredis`, or `queue-bullmq`. Synthetic boundary fixtures exercise each of the three allowed canonical built-ins in both `file/` and `src/file.ts`. Representative disallowed canonical, bare, and subpath built-ins are deliberately distributed across the two scopes; the fixtures do not claim that every disallowed example is duplicated in both.

The behavior is pinned by [`file-checkpointer.test.ts`](../../packages/framework/src/__tests__/file-checkpointer.test.ts), [`file-freshness-index.test.ts`](../../packages/framework/src/__tests__/file-freshness-index.test.ts), [`file-resume.test.ts`](../../packages/framework/src/__tests__/file-resume.test.ts), [`file-event-record.test.ts`](../../packages/framework/src/__tests__/file-event-record.test.ts), [`file-job.test.ts`](../../packages/framework/src/__tests__/file-job.test.ts), [`file-journal.test.ts`](../../packages/framework/src/__tests__/file-journal.test.ts), [`file-boundary.test.ts`](../../packages/framework/src/__tests__/file-boundary.test.ts), and [`file-boundary-error.test.ts`](../../packages/framework/src/__tests__/file-boundary-error.test.ts). These cover exhaustive typed-kind/operation assertions, compile-time rejection of misspelled file operations while preserving public string operations, hostile thrown-value corpora, throwing getters/proxies/clocks/decoders/machines, logger failures, deep hostile records, typed filesystem failures, and path-escape attempts, with no assertion that a public throw has an undefined kind.

## Consequences

**Positive:**
- Every operational port that can carry an error returns a typed `Result`; hostile runtime behavior cannot turn those methods into raw rejected promises.
- Failed journal writes and owned-lock releases abort transitions, preserving append-before-checkpoint durability and preventing false success with a live lock left behind.
- Existing `FrameworkError` kinds and operation fields preserve Redis/backend-swap parity without forcing consumers to handle a new file-specific variant.
- Required corruption observability is honest: a failed logger does not silently convert a required warning into apparent success.
- Total diagnostic helpers preserve the original failure even when the thrown value itself is hostile to inspection.
- The backend remains dependency-free and broker-independent under FR-041/FR-043.

**Negative:**
- Consumers of the file subpath must understand both `Result`-returning operations and the throwing `JobLike`/journal/serializer transport, even though both carry only `FrameworkError` values.
- The existing `cache-error` kind now covers both infrastructure failures and runtime-invalid values on throwing-only surfaces; consumers distinguish them by the exact `operation` and contextual message rather than a new kind.
- Resume intentionally classifies any unreadable authoritative event log as `checkpoint-corrupt`, even when the preserved diagnostic indicates an environmental I/O cause, favoring proof and fail-closed safety over fine-grained availability handling.
- Treating logger failure as `cache-error` can turn an otherwise recoverable corrupt-entry drop into a failed load/query, accepting reduced availability to preserve required observability.
- Defensive snapshots, strict codecs, bounded hostile-data walks, release-outcome arbitration, and contextual error construction add implementation complexity and test surface.
- A release failure can reject an append after its event rename committed. Callers must apply the existing idempotent retry discipline and may need to remediate the reported live lock; rejection intentionally means the whole append operation was not cleanly completed, not that no bytes committed.
- The broker ban, no-new-package constraint, and exact `node:*` allow-list add a strict maintenance gate: adopting another Node built-in requires an explicit FR-041 decision and corresponding rule change rather than passing through by source-audit oversight.

## Amendment (2026-08-18)

The original FreshnessIndex row listed "lock" among the failure classes returning `cache-error` under `freshness:recordWrite` / `freshness:findConflict`, but the shipped code let lock-protocol failures RIDE THROUGH under their own operations — a squatted lock path surfaced as `acquireFileLock`, and a body-internal commit failure (the `atomicWriteFile` error wrapped by `withFileLock`) surfaced as `withFileLock`. The row, the pinned ride-through test, and the journal's behavior (which re-tags at its public `appendEvent` boundary) disagreed with one another on the operation field.

The amendment makes the journal's behavior the contract: the closed lock-protocol set (`acquireFileLock` / `withFileLock` / `releaseFileLock` / `stealStaleFileLock`, defined once beside `FileOperation` in `file/boundary-error.ts`) is re-tagged at the freshness public surface to `freshness:recordWrite` / `freshness:findConflict`, preserving the inner `failureClass` and the full diagnostic chain (lock path, the primary body failure nested inside the `withFileLock` diagnostic). The operation field always names the caller's port call, exactly as the journal's `appendEvent` row states. Pinned in `file-freshness-index.test.ts`: the lock-squatter acquire case asserts `freshness:recordWrite` with the lock path and inner `acquireFileLock` diagnostic in the message, and a deterministic body-internal commit failure (test-only `atomicWriteFileHooks` seam) asserts `freshness:recordWrite` with the `withFileLock`/`atomicWriteFile` chain preserved.
