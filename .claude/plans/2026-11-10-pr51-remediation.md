## Advisory dispositions — slice A

- **A/code-reviewer-1** — accepted — `packages/xlsx/src/zip.ts`
  - Claim: inflateEntry's fast path allocates a buffer sized from the attacker-controlled declared uncompressedSize (up to the 512 MiB cap) before any inflation, regardless of the real compressed size.
  - Reviewer reason: A hostile workbook can declare a near-cap uncompressed size for small parts such as [Content_Types].xml, styles or sharedStrings. Each part then triggers a transient allocation of up to about 512 MiB, which weakens the memory bound this change is meant to provide. Zero-filled allocations are often lazily committed, so real impact may be small. Consider a tighter cap for the metadata parts, or allocating from min(declared, a small multiple of compressedSize) and falling back to the streamed path when the buffer fills.
  - Disposition reason: Sound: the fast path trusts the attacker-declared uncompressedSize for its allocation, weakening the memory bound the PR exists to provide; bound the preallocation by the compressed size and fall back to the streamed path.
- **A/silent-failure-hunter-1** — dismissed — `packages/xlsx/src/index.ts`
  - Claim: foldRows rejects an invalid yieldEveryBytes with a node-crash, but does not validate headerRow. A headerRow of 0, a negative, fractional or NaN value, or one past the last row, silently yields ok with zero rows.
  - Reviewer reason: With a headerRow that never matches an emitted row index, `fold.headers` stays null. `projectRow` then runs against the empty `NO_HEADERS` map, so every row is skipped as blank and the fold returns `ok(init)` with no error. This matches the old SheetJS parser, so it is not a regression. The new contract is explicit about the other option, since `yieldEveryBytes` is validated and the documented node-crash list is exhaustive. Failing loudly on a non-positive-integer `headerRow`, or on a sheet that ends before the header row, would turn a silent empty result into an actionable error. This does not block delivery.
  - Disposition reason: parseWorkbook must keep the SheetJS contract exactly (FR-030); SheetJS returns ok with zero rows for an out-of-range headerRow, so failing here would be a contract change, not a fix.
- **A/silent-failure-hunter-2** — accepted — `packages/xlsx/src/index.ts`
  - Claim: After the fold reports `done` (a row past the dimension's last row), foldRows returns ok(fold.acc) even if the XML write in that chunk failed, and it stops reading the rest of the sheet. Malformed or truncated worksheet XML after that point is never reported.
  - Reviewer reason: The loop checks `failure`, then `done`, and only then `written.ok`. A malformed tail therefore yields a successful result where the documented contract says malformed XML is a node-crash. SheetJS, the reference, would have thrown on malformed XML. Rows before the cut-off were already validated, so the practical exposure is small. Document the early-exit behaviour, or keep draining and validating the XML.
  - Disposition reason: Sound: a chunk that both ends the fold and fails XML parsing must report the node-crash; check the write result before honouring done, and document that bytes past the dimension's last row are not parsed.
